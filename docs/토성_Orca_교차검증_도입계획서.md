## 1. 개요 및 목적

토성 시스템은 현재 단일 AI 에이전트(Claude Code 등)가 코드를 직접 수정·반영하는 방식으로 개발되고 있다. 이 방식은 빠르지만, 에이전트의 환각(Hallucination)이 곧바로 메인 코드베이스에 유입되는 구조적 리스크를 안고 있다.

본 계획서는 영상에서 실증된 **4단계 교차검증 워크플로우**(작업 배정 → 에이전트별 코딩 → Diff 비교 → 최선 코드 머지)를 Orca ADE(Agent Development Environment) 기반으로 토성 시스템에 이식하여, 다음을 달성하는 것을 목적으로 한다.

1. **무결성:** 복수 에이전트(Claude Code + Codex)의 결과물을 교차 심사하여 환각 코드의 메인 브랜치 유입을 차단한다.
2. **품질 상향:** 동일 과제에 대한 서로 다른 모델의 접근법 중 최선의 구현만 채택한다.
3. **역할 전환:** 개발자는 '작성자(Writer)'에서 '설계자·심사자(Architect/Reviewer)'로 전환하고, 심사 기준은 대화가 아닌 **Git Diff + 테스트 결과**라는 객관적 지표로 삼는다.

### 2.2 핵심 격차(Gap) 요약

- **G1. 로컬 Git 미정착** → 워크트리 기반 격리 자체가 불가능
- **G2. 테스트 부재** → 승자 판정의 객관 기준 부재
- **G3. 단일 파일 구조** → 병렬 작업 시 Diff가 한 파일에 집중되어 비교 효율 저하
- **G4. 에이전트 1종 운용** → 교차검증에 필요한 '경쟁 상대'(Codex 등) 미구축

## 3. 목표 아키텍처 (To-Be)

영상의 4단계 워크플로우를 토성에 다음과 같이 매핑한다.

```
[토성 저장소 (origin/main = Base Ref)]
        │
        │ ① 작업 배정: 단일 프롬프트 팬아웃
        ├──────────────────────┬──────────────────────
        ▼                      ▼
[워크트리 A]              [워크트리 B]
 task-claude               task-codex
 Claude Code 자율 코딩      Codex 자율 코딩          ← ② 에이전트별 코딩 (완전 격리)
 자체 npm test 실행         자체 npm test 실행
        │                      │
        └──────────┬───────────┘
                   ▼
        ③ Diff 비교 (Orca 내장 Diff 뷰어)
        심사 기준: 테스트 통과 → 수치 정합성 → 설계/의존성 → 부작용
                   │
                   ▼
        ④ 최선 코드 머지 (승자만 commit/push, 패자 워크트리 rm)
```

- 각 워크트리는 `.git`을 공유하되 **물리적으로 독립된 폴더**이므로, 어느 에이전트가 코드를 훼손해도 메인과 상대 작업 공간에 영향이 없다.
- 비용 모델은 BYO(Bring Your Own Subscription): Orca 자체는 MIT 무료이며, 기존 보유한 Claude 구독과 OpenAI 자격 증명을 그대로 연결한다.

## 4. 단계별 실행 계획

### Phase 0 — 저장소 정비 (선행 조건 해소, 소요 약 0.5일)

교차검증의 토대인 Git 워크플로우를 정착시킨다.

1. `C:\Users\silro\Desktop\토성` 폴더에서 로컬 Git 초기화 및 원격 연결:
   ```powershell
   cd C:\Users\silro\Desktop\토성
   git init
   git remote add origin https://github.com/silro742/bim.git
   git fetch origin
   git checkout -b main origin/main   # 원격 이력을 기준점으로 채택
   ```
2. 로컬 파일과 원격 저장소를 동기화하여 **`origin/main`을 유일한 Base Ref**로 확립한다. 이후 "Add files via upload"(웹 업로드) 방식은 중단하고 모든 반영은 commit/push로 일원화한다.
3. `.gitignore` 작성 (`node_modules/`, 워크트리 폴더, 캐시 등).
4. 브랜치 규칙 확정: `main` = 검증 통과 코드만 존재. 에이전트 작업은 전부 워크트리 브랜치(`task-*`)에서만 수행.

**완료 기준:** 로컬에서 `git status`가 깨끗하고, `git push origin main`이 정상 동작한다.

### Phase 1 — 검증 기반 구축: 모듈 분리 + 테스트 하네스 (소요 약 1~2일)

영상의 심사 1순위 기준(테스트 통과)을 토성에서 실행 가능하게 만든다. **이 단계가 본 계획의 성패를 좌우한다.**

1. **코어 로직 분리:** HTML 내장 JS에서 순수 계산 함수를 ES 모듈로 추출한다.
   - `src/core/delaunay.js` — `delaunayTriangulate`, `computeCircum`
   - `src/core/tin.js` — `TINSurface` (`findTriangle`, `getElevation`, `calculateSlope`)
   - `src/core/hydrology.js` — `traceWaterDrop`, `delineateCatchment`
   - `src/core/analysis.js` — `analyzeSurface` (표고/경사 밴드)
   - `src/core/compliance.js` — `checkCompliance`, 법규 데이터
   - UI(캔버스 렌더링, 패널)는 HTML에 남기고 `<script type="module">`로 코어를 import한다.
2. **테스트 하네스:** Node 내장 테스트 러너(`node --test`) 또는 Vitest 채택. 브라우저 없이 터미널에서 `npm test` 한 줄로 실행 가능해야 각 워크트리의 에이전트가 자율적으로 검증을 돌릴 수 있다.
3. **골든 테스트 작성 (최소 세트):**
   - 딜로니: 정사각형 4점 → 삼각형 2개, 공선(collinear) 점 처리, 중복점 처리
   - 표고 보간: 평면 3점 위 임의 좌표의 EL 해석해 대비 오차 < 1e-9
   - 경사도: 알려진 두 점 간 경사(%·도·비율) 수기 계산값 일치
   - 워터드롭: 단순 경사면에서 최급강하 방향 추적, `maxSteps` 내 종료 보장
   - 유역면적: 대칭 지형에서 유역 대칭성 검증
   - 법규: 한국 배수 기준(일반 1.0%, 도로 횡단 1.5%, BF 경사로 8.33% 등) 경계값 판정
4. **분리 작업 자체를 첫 교차검증 리허설로 활용해도 좋으나**, 기준 테스트가 아직 없으므로 이 단계만은 단일 에이전트 + 수동 검토로 진행하는 것을 권장한다.

**완료 기준:** `npm test` 전체 통과, HTML 앱이 분리 전과 동일하게 동작(수동 확인).

### Phase 2 — Orca 설치 및 온보딩 (소요 약 0.5일)

1. **설치 (Windows):** 공식 다운로드 페이지에서 `orca-windows-setup.exe`를 받아 설치한다.
   - 주의: macOS의 `brew install --cask orca`는 전혀 다른 도구(Plotly Orca)가 설치되는 함정이 있다. Windows에서는 해당 없음이나, 반드시 **stablyai 공식 배포 채널**에서만 받는다.
2. **온보딩:**
   - 홈 디렉터리 접근 권한 허용 → 기존 `~/.claude`, `~/.codex` 설정 자동 임포트
   - 기본 에이전트(Default Agent)로 Claude Code 지정
   - **시스템 알림 활성화** (백그라운드 워크트리 완료 감지에 필수)
   - 'Add Repo'로 `C:\Users\silro\Desktop\토성` 매핑 → Base Ref가 `origin/main`으로 자동 할당되는지 확인
3. **경쟁 에이전트 구축:** Codex CLI를 전역 설치(`npm i -g @openai/codex`)하고 API 키 로그인까지 완료한다. Orca 에이전트 목록에서 Claude Code / Codex 두 개가 모두 인식되는지 확인한다.
4. **권한 우회 플래그에 대한 인지:** Orca는 무인 실행을 위해 Claude에 `--dangerously-skip-permissions`, Codex에 `--dangerously-bypass-approvals-and-sandbox`를 자동 주입한다. 워크트리는 일회용 공간이므로 허용 가능하나, **이 플래그가 적용된 에이전트에게는 절대 메인 작업 폴더나 저장소 밖 경로를 다루게 하지 않는다**는 원칙을 세운다.

**완료 기준:** Orca에서 토성 저장소가 보이고, 테스트 워크트리 1개를 생성·삭제할 수 있다.

### Phase 3 — 파일럿 교차검증 (소요 약 1일)

실전 투입 전, 결과 비교가 쉬운 과제로 전체 사이클을 1회 완주한다.

**파일럿 과제(권장):** "`traceWaterDrop`이 평탄 지역(경사 ≈ 0)에서 조기 종료되는 문제를 개선하고, 지역 최저점(local minimum) 도달 판정을 추가하라. 관련 단위 테스트 포함."

1. **워크트리 생성 (팬아웃):**
   ```
   orca worktree create --repo path:토성 --name waterdrop-fix-claude
   orca worktree create --repo path:토성 --name waterdrop-fix-codex
   ```
2. 각 워크트리 탭에 Claude Code / Codex를 매핑하고 **동일 프롬프트를 복사·전송**한다. 프롬프트에는 반드시 "`npm test`가 전부 통과해야 한다"를 명시한다.
3. **상태 지시등 관제:** 🟢(작업 중) 관망 → 🟡(질문 대기) 즉시 응답 → ⚪(완료) Diff 심사 개시.
4. **Diff 심사 (§5 기준표 적용):** 두 워크트리에서 각각 `npm test` 실행 → 결과·구현 비교 → 필요 시 'AI Diff 주석'으로 특정 라인에 인라인 코멘트를 남겨 해당 에이전트에게 직접 재수정 지시.
5. **머지 및 GC:** 승자 워크트리에서 변경분만 스테이지 → 커밋 → `origin` 푸시. 패자 폐기:
   ```
   orca worktree rm waterdrop-fix-codex   # (또는 -claude, 패자 쪽)
   ```

**완료 기준:** 4단계 사이클 1회 완주, 심사 기록(어느 에이전트가 왜 이겼는지) 1건 문서화.

### Phase 4 — 표준 운영 프로세스(SOP) 확립 (파일럿 직후)

파일럿 경험을 바탕으로 다음을 토성 개발의 기본 규칙으로 고정한다.

- **교차검증 대상:** 코어 알고리즘 수정, 법규 데이터 변경, 신규 기능 등 **정답이 갈릴 수 있는 모든 과제**. (오탈자·주석 등 사소한 수정은 단일 에이전트 허용)
- **워크트리 수명 규칙:** 머지 즉시 잉여 워크트리 `rm`. 3개 이상 동시 오픈 금지(§7.2 리소스 병목 예방).
- **프롬프트 규격:** ① 요구사항 ② 제약(의존성 추가 금지 등) ③ "단위 테스트 작성 + `npm test` 통과" ④ 완료 조건 — 4요소를 항상 포함해 양쪽에 동일하게 전송.
- **UI 과제의 시각 피드백:** 프론트엔드 수정 시 워크트리 내에서 `npx serve`(또는 `npm run dev`)로 로컬 서버 구동 → Orca 내장 브라우저 + **디자인 모드**로 대상 컴포넌트를 클릭해 DOM 맥락과 크롭 스크린샷을 에이전트에 직접 전달한다. 캔버스 기반 화면(지형 렌더링)은 DOM 타게팅이 제한되므로 스크린샷 + 좌표 서술로 보완한다.
- **모바일 관제(선택):** 장시간 리팩토링 시 Orca 모바일 동반 앱(iOS/Android)을 페어링해 완료 푸시 알림 수신 및 원격 인터럽트를 활용한다.

### Phase 5 — 자동화 확장 (중기, 필요 시)

## 5. Diff 심사 기준표 (토성 전용)

영상의 3대 기준을 토성 특성에 맞게 구체화한 채점표. 상위 항목이 우선하며, 1번 탈락 시 즉시 패배 처리한다.

| 순위 | 기준 | 토성에서의 구체적 확인 방법 |
| :--- | :--- | :--- |
| 1 | **테스트 스위트 통과** | 각 워크트리 터미널에서 `npm test` 실행. 실패 = 즉시 탈락 |
| 2 | **수치 정합성** | 표고·경사·유역 결과를 골든 값(수기 계산/기존 검증값)과 대조. BIM 산출물은 법적 근거 자료가 되므로 소수점 오차도 심사 |
| 3 | **법규 로직 보수성** | `checkCompliance` 관련 변경 시 경계값(예: 8.33%)에서 완화 방향의 오판이 없는지 확인 |
| 4 | **설계·유지보수성** | 시간 복잡도, 불필요한 서드파티 의존성 추가 여부(토성은 무의존성 유지가 원칙), 기존 코드 스타일 준수 |
| 5 | **부작용 고립성** | 요청 범위 밖 파일 수정 여부, UI 동작 회귀(수동 스모크: Load Sample Surface → 7단계 순회) |
| 6 | **테스트 커버리지 품질** | 추가된 테스트가 경계 조건(공선점, 평탄지, 경계 외 좌표)을 실제로 방어하는지 |

동점 또는 양쪽 모두 결함 시: 'AI Diff 주석'으로 결함 라인에 인라인 피드백 → 재수정 → 재심사 루프를 돌린다. 두 결과물의 장점을 합치고 싶을 때도 **직접 손 머지하지 말고**, 승자 워크트리의 에이전트에게 "패자의 이 접근을 반영하라"고 주석으로 지시하는 방식을 우선한다.

## 7. 리스크 및 트러블슈팅

### 7.1 Windows 전역 스킬 충돌 (좀비 스킬)

Orca 전역 설치 시 `%USERPROFILE%\.agents\skills\computer-use\SKILL.md` 등에 스킬·훅이 등록되며, Orca 삭제 후에도 잔존하여 Codex가 존재하지 않는 `orca` CLI를 호출하다 실패하는 충돌이 보고되어 있다.
- **예방:** 설치 직후 `%USERPROFILE%\.agents\.skill-lock.json`에서 `stablyai/orca` 항목을 확인해 두고, 제거 시 `%LOCALAPPDATA%\Orca` 및 `.agents` 하위 잔여물을 수동 점검·삭제한다.

### 7.2 리소스 병목

워크트리마다 파일 감시자 + Node 프로세스 + Chromium 인스턴스가 붙는다. 토성 운용 규칙: **동시 워크트리 최대 2개(파일럿)~3개**, 심사 완료 즉시 `rm`, 내장 브라우저 탭은 검토 후 즉시 닫기.

### 7.3 워크트리 생성 실패

"기준점(Start-from ref)을 찾을 수 없음" 오류 → 저장소에서 `git fetch origin` 후 재시도. 동명 워크트리/브랜치 잔존 시 이름 변경 또는 선제 삭제.

### 7.4 권한 우회 플래그의 보안 리스크

`--dangerously-*` 플래그는 워크트리라는 일회용 격리 공간을 전제로만 허용한다. **토성 메인 폴더에서 이 플래그로 에이전트를 직접 구동하는 것을 금지**하고, 민감 자격 증명 파일은 저장소 밖에 보관한다.

### 7.5 단일 파일 병합 충돌

Phase 1 완료 전에는 두 에이전트의 변경이 모두 한 HTML에 몰려 Diff 심사가 어렵다. **Phase 1(모듈 분리)을 건너뛰고 Phase 3에 진입하지 않는다.**

### 7.6 API 비용

교차검증은 태스크당 토큰 소비가 약 2배가 된다. 완화책: 사소한 수정은 단일 에이전트로 처리(§Phase 4 기준), 교차검증은 코어 로직·법규 변경에 집중.
